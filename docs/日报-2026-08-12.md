## 交付

### 1. 审核弹窗顶部的一行提炼

根因不是"信息多"，是那段内容本来就是 `JSON.stringify(display_block)` —— 一次编辑会把前后全文当 JSON 糊在屏幕上。

新增纯函数 `approval-summary.ts`，按信息量而非请求构造顺序取值：有 diff 就报路径和行数，其次命令、wiki、待办、后台任务，都没有才退回描述首行、再退回 `工具 · 动作`。display block 序列化后是扁平结构，但部分生产者嵌在 `data` 下，所以每个字段读取都兼容两种形态。原始 JSON 收进折叠区。9 个测试。

### 2. Plan 右侧的 YOLO 开关

走 plan mode 的既有链路：新增 `set_yolo` RPC + `StatusUpdate.yolo`。

刻意做成 set 而不是 toggle —— 终端 `/yolo` 和第二个客户端都会动这个状态，toggle 会把客户端最后看到的值取反。`/yolo` 现在也发 StatusUpdate，双向同步；`initialize` 汇报当前值，因为 `--yolo` 可以在任何 wire 消息之前就打开，且不像 plan mode 那样能靠 replay 重建。

顺带修正 git-bash 横幅的判断依据（新增 `shell_available`），否则靠便携 shell 正常跑命令的机器会被一直误报"请安装 Git for Windows"。

### 3. 切换会话的滚动定位

**这条第一次修错了，值得记下来。**

第一次诊断：滚动状态跨会话残留（`catchUpRef` 活过了会话切换，因为只有内层 Virtuoso 带 key）。这确实是个真问题，也修了，但不是用户遇到的那个 —— 复测仍然跳到顶部。

第二次改用实测。应用有登录墙，没有动用户账号，而是搭了一个只含 Virtuoso + 真实滚动策略的最小复现页，用无头 Chromium 量 `scrollTop`。数据直接推翻了假设：200 条消息分 10 批回放，`followOutput` **十次全部返回 `"auto"`**，catch-up 全程 armed，位置依然不对。

真因：`followOutput` 滚到最后一条时，刚加进去的条目还在用 `defaultItemHeight`（160px）估算高度；真实消息远比这高，等它们被测量出来，内容底部就往下跑了，而此时条目数已不再变化，`followOutput` 不会被第二次问到。**估算错多少，就停在离底部多远的地方** —— 复现里差 21,006px；真实会话里长回答和工具输出动辄几千 px，看起来就是"跳到最上面"。

改法：catch-up 期间不只跟随条目数，也跟随列表总高度。滚动到某个 index 本身不改变高度，所以会收敛而不是自激；读者第一次滚轮/触摸/按键即解除。它同时覆盖"切到更短的会话"那条路径——条目数不增长，但总高度会变。

## 一处自己的失误（已修正）

给用户的版本核对方法（比对 `index-*.js` 哈希）不可靠：`assets/` 下有 6 个 `index-*` 文件，`head -1` 取到的是 2KB 的入口 chunk，不是浏览器加载的 220KB 主 chunk，导致用户看到的 URL 与我给的哈希对不上。

正确做法是搜特征字符串：

```
grep -rl "totalListHeightChanged" /Applications/OpenKimo.app/Contents/Resources/kimi_cli/web/static/assets/
```
