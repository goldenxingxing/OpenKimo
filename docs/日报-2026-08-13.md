## 1. 第一份日志：端口冲突，以及三个撑住它的缺陷

**现象**：`[WinError 10048]` 每 2 秒一次，**947 次、一个半小时**，界面上只表现为会话掉线。

**直接原因**：一台机器上跑了两个实例，09:45 那个绑定成功并一直正常服务（10,177 条请求），09:55 启动的第二个永远抢不到端口。

**为什么会永远转下去**——三个独立缺陷叠在一起：

1. **健康检查从来没有在检查任何东西**。守护进程探的是 `/health`，而这个路由**根本不存在**：SPA 兜底路由 `@application.get("/{full_path:path}")` 对任何 GET 返回 index.html + 200，而判断只是 `200 <= status < 500`。于是任何端口都"健康"，包括别人占着的那个；刚死于 10048 的子进程被判为 RUNNING → 重启计数器清零 → `MAX_AUTO_RESTARTS = 3` 形同虚设。
   - 实测：`/health` → 200 text/html；`/healthz` → 200 `{"status":"ok","pid":…}`。
2. **没有任何东西清理残留监听者**。`_reap_orphan_listener` 调 `lsof` 和 `ps`，Windows 上两个命令都不存在，整个函数被 `except Exception: return` 吞掉。而 `app_main_win/server.py` 的注释写着"supervisor 是平台中立的，直接复用 macOS 那份"——它不是。
3. **没有任何东西阻止开第二个实例**。全仓库没有任何单实例保护。

**改动**：
- 探针改到 `/healthz`，要求 JSON 且 `status == "ok"`，并把响应里的 `pid` 与自己 spawn 的子进程比对（`/healthz` 新增 pid 字段）。一个 HTML 页面配 200 不是健康检查。
- Windows 版 reaper：`netstat -ano` 定位 → PowerShell `Get-CimInstance` 读命令行 → 只杀命令行含 `kimi_cli.web.app` 的进程，绝不按端口盲杀。
- 命名内核 mutex 做单实例（进程被强杀时系统自动释放句柄，pidfile 做不到）。第二次启动**打开已有实例的页面**再退出，而不是静默消失——点了没反应的图标本身就是故障。
- 端口确实被占用时不再 spawn，托盘显示 `Port 5494 in use — close the other copy`；CRASHED 变成 watcher 不会覆盖的终态（否则诊断会在半秒后被 "Stopped" 抹掉）。
- `uvicorn-log.json` 改原子写，修掉日志里那两次 `JSONDecodeError`（两个实例并发读写同一个文件）。

## 2. 第二份日志：WebSocket 403，与端口无关

端口冲突在 12:03 已经解决（绑定成功、不再有 10048），但症状还在：

```
12:04:44  "WebSocket /api/sessions/…/stream" 403  ← 连续 6 次
12:05:14  "GET /api/memory/recent" 200 OK          ← 同期 HTTP 全部正常
```

**根因**：HTTP 和 WebSocket 的鉴权条件不一致。`AuthMiddleware` 在设置了 session token 时接受**两种**凭据——session token **或**有效的 `kimi_session` 登录 cookie（这个 fallback 是特意写的）；而 WebSocket 端点只认 `?token=`。"设置里填了 Session Token + 用账号密码登录"这个组合于是精确落进：每个 HTTP 请求 200，每个握手被拒。

**改动**：凭据解析抽成 `user_from_connection(connection: HTTPConnection)`——一次握手和一个请求带着同样的 cookie 和 header，两条路径走同一条规则。客户端把 4401/4403 归入终态 close code（重试 5 次不可能改变一个已经说明的拒绝），并按服务端真正说的原因给文案。

## 3. 顺带解释清楚的 405

`POST /api/does-not-exist` → **405 而不是 404**（实测）。因为 SPA 兜底路由只接受 GET：路径匹配上了、方法不匹配，Starlette 就返回 405。**所以在这套代码里 405 基本只意味着一件事：前端用非 GET 调了一个后端没有的接口**，最常见的成因是前端比后端新。和 `/health` 那条是同一个根源。

## 未验证的部分（重要）

三条 Windows 改动**都没有在真机验证过**——需要 Windows。逻辑和边界用单测覆盖了（netstat 输出按真实格式构造），但 `netstat` / `powershell` / `taskkill` 的实际行为和 mutex 的实际生效只能靠复测。装上 v0.1.32 后建议按这个顺序验：

1. 设置窗口里 **Session Token 是否有值** —— 有值则第 2 节那条直接对症；仍然 403 说明是 LAN Only 或 Origin 守卫，需要再查。
2. 再点一次图标，应打开已有页面而不是又起一个；`server.log` 不该再有 10048。
3. 故意用别的程序占住 5494 再启动 → 托盘应显示 `Port 5494 in use`。
4. 强杀托盘进程（留下 uvicorn）再启动 → 应能自动清理。
